次の対象について、要件を整理してください: $ARGUMENTS

`$ARGUMENTS` がファイルのパスなら、そのファイル(メモ・既存資料・依頼文など)を入力として読んでください。

## 手順

1. **現状を把握する。** `CLAUDE.md`、`.claude/rules/`(技術スタック・注意事項など)、`docs/` 配下の既存資料、関連コードを読む。この会話で既に決まっていること(技術、方針、やらないこと)があれば、それを前提にする。推測で進めない。
2. **足りない情報を洗い出す。** 次の観点で、決まっていないことを探す。
   - 目的・成功の基準(何ができたら成功か)
   - 対象ユーザーと利用シーン
   - 機能の範囲(必須 / あると良い / やらない)
   - データ・入出力(何を扱うか、制約)
   - 非機能(セキュリティ、性能、アクセシビリティ、対応環境)
   - 外部との連携、既存機能への影響
3. **質問する。** 回答で結果が変わる重要なものだけを、**最大5個、まとめて**質問する。各質問には、選択肢か、おすすめの案を添える。回答を待つ。
   - 既に分かっていること、コードを読めば分かること、結果に影響しないことは、質問しない。
4. **回答を受けて、`docs/spec.md` に次の構成で書く**(既にあれば、内容を保って追記・更新)。
   - 目的と背景
   - 対象ユーザーと利用シーン
   - 機能要件(必須 / あると良い / 今回やらないこと)
   - 非機能要件(セキュリティ、性能、アクセシビリティ など)
   - 完了条件(チェックリスト。検証できる形で書く)
   - 未決事項
5. **推測した内容は、事実と区別する。** 回答がなく、推測で埋めた項目には「【仮定】」と付け、未決事項にも載せる。
6. 要約、仮定した項目、未決事項を報告し、確認を待つ。

## 制約

- ソースコードは変更しない(`docs/spec.md` の作成・更新のみ)。
- 仕様にない機能を追加しない。依頼されていない要件を、善意で足さない。
- 完了条件は、「見やすい」のような曖昧な書き方をしない。数値、操作、結果で書く。
