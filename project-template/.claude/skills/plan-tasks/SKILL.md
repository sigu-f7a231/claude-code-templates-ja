`docs/spec.md` を読み、次の対象の実装計画を作ってください: $ARGUMENTS

## 手順

1. `docs/spec.md` と関連する既存コードを読む。`docs/spec.md` がなければ、先に `/spec` の実行を提案して止まる。
2. 影響する範囲(ファイル・モジュール・データ)を洗い出す。
3. 作業を、**1ステップ = 1つの検証可能な変更**になるよう分解する。1タスクは、1回の `/implement` で終わり、確認方法が1つに決まる大きさにする。確認方法を書けないタスクは、大きすぎるか曖昧なので分け直す。順序は、土台 → データ → API → 画面 → 仕上げの順を基本にし、依存関係を書く。各タスクに次を書く。
   - 番号とタイトル
   - 変更するファイル(予定)
   - 完了の確認方法(テスト、コマンド、画面での確認)
   - 依存するタスク
4. リスクと代替案(技術選択が複数ある場合は2案を比較)を書く。
5. `docs/plan.md` に保存し、要約を報告して**承認を待つ**。

## 制約

- ソースコードは変更しない(`docs/plan.md` の作成・更新のみ)。
- 承認前に実装を始めない。
- GitHub Issue は作らない(計画は `docs/plan.md` に書くだけ。Issue にしたい場合は、人が `/plan-to-issues` を実行する)。
