# 指示を出すところから公開前までの作業の流れ

<!--
  最初の指示から公開前までを、貼り付けられる指示文つきで順に説明する手順書。
  置き場所: read/(雛形集の解説)。自分のプロジェクトの docs/ にコピーしても使える(その場合、../prompts/ など雛形集のパスは参照できない)。
  【 】は自分のプロジェクトに合わせて書き換える。
  関連: 指示テンプレートは ../prompts/、工程別の Skills は ../project-template/.claude/skills/。
-->

最初の指示を出してから、公開前のチェックまでを、順番に進める手引きです。各ステップに「貼り付ける指示」「Claude が返すもの」「あなたが確認すること」を書いています。


## 全体の流れ

```text
Step 0  準備                  フォルダ・git・テンプレートの配置
Step 1  最初の指示             何を作るかを伝える(質問と提案だけをさせる)
Step 2  質問に答える・方針を決める
Step 3  CLAUDE.md と Rules を作る  決めた技術・コマンド・規約を記録(/init)
Step 4  要件を整理する          /spec  → docs/spec.md
Step 5  計画を立てる            /plan-tasks → docs/plan.md(承認)
Step 6  タスクを1つずつ進める   ( /implement → /test → /review → /commit ) を繰り返す
Step 7  公開前のチェック        /release
Step 8  公開(人が行う)
```

| ステップ | 動かすもの | 出力(残るもの) |
|---|---|---|
| 1〜2 | 指示(プロンプト) | 技術・方針の合意(会話の中) |
| 3 | `/init`、CLAUDE.md | `CLAUDE.md` |
| 4〜5 | `/spec`、`/plan-tasks` | `docs/spec.md`、`docs/plan.md` |
| 6 | `/implement` ほか | コード、テスト、コミット、`plan.md` の進捗 |
| 7 | `/release` | チェック結果、リリースノート案 |

---

## コマンド早見表(日本語で意味を確認する)

`/名前` は、あらかじめ用意した「手順書(Skill)」を呼び出す合図です。名前の後ろに書いた文字は、その手順書への**追加の情報(引数)**になります。

```text
/implement 3
 │         └─ 引数: 「docs/plan.md のタスク3番」という意味
 └─ コマンド名: 「実装する」手順書を呼び出す
```

| コマンド | 日本語での意味 | いつ使う | 引数(後ろに書くもの) | 書き方の例 | 何が起きるか(一言) |
|---|---|---|---|---|---|
| `/spec` | 要件を整理する | 作る前に、何を作るか決めたいとき | 作るものの概要、または資料のファイル名 | `/spec ToDo アプリ` | 質問に答えると、`docs/spec.md`(仕様書)ができる |
| `/plan-tasks` | 作業を計画する(タスクに分ける) | 仕様が固まって、作業の順番を決めたいとき | 計画する機能名、または「全体」 | `/plan-tasks 全体` | `docs/plan.md`(作業リスト)ができる。承認するまで実装しない |
| `/implement` | 計画の1つの作業を実装する | 計画の承認後、**1つずつ**作るとき | **`docs/plan.md` のタスク番号**(必須) | `/implement 3` = タスク3を実装 | コードとテストを書き、結果を報告する(コミットはしない) |
| `/test` | テストを実行して直す | 実装のあと、動作を確認したいとき | 対象のファイル名(省略可) | `/test` | テストを実行し、失敗があれば原因を調べて直す |
| `/review` | 変更をレビューする(点検する) | コミットの前に、問題がないか見たいとき | 重点的に見たい観点(省略可) | `/review` | 変更内容を点検し、問題点を一覧で報告する(ファイルは変更しない) |
| `/commit` | 変更を記録する(コミットする) | 1つの作業が終わって、区切りをつけるとき | メッセージの方針(省略可) | `/commit` | 変更を git に記録する(`push` はしない) |
| `/release` | 公開前のチェックをする | すべての作業が終わったとき | バージョン名(例: `0.1.0`) | `/release 0.1.0` | チェック結果とリリースノート案を出す(公開はしない) |

### 「`/implement 3` の `3`」とは

`docs/plan.md` に並んでいるタスクの**番号**です。計画の中身は、こう並んでいます。

```text
- [x] 1. プロジェクトの土台        ← 完了
- [x] 2. DB とマイグレーション      ← 完了
- [ ] 3. ToDo の追加 API と入力検証  ← これを実装したいなら /implement 3
- [ ] 4. 一覧表示と完了の切り替え
```

- `docs/plan.md` を開いて、**次にやりたいタスクの番号**を書きます。
- 番号が分からないときは、タイトルでも送れます: `/implement ToDo の追加 API と入力検証`
- 迷ったら、先に「`docs/plan.md` を見て、次にやるタスクを教えて」と聞きます。

### 1つのタスクでの使う順番

```text
/implement 3   →   /test   →   /review   →   /commit
 (作る)          (動作確認)    (点検する)     (記録する)
```

- 覚え方: **作る → 確かめる → 点検する → 記録する**
- `/review` は、**記録する(`/commit`)前**に使います(まだ記録していない変更が点検の対象のため)。

## Step 0: 準備

```bash
mkdir 【プロジェクト名】 && cd 【プロジェクト名】
git init
mkdir -p .claude/skills .claude/rules .claude/agents .claude/hooks docs
```

`../project-template/` から、必要なものを自分のプロジェクトにコピーします(`CLAUDE.md`、`.claude/`、`docs/`。配置先は `../project-template/README.md` を参照)。

- 最小構成: `skills/`(7つ)だけでも動きます。
- 推奨: `settings/settings.json`(`push` や `.env` の拒否)、`hooks/*.sh`(`chmod +x`)、`rules/`、`agents/`。

Claude Code を起動します。

```bash
claude
```

**確認すること**

- `/` を入力すると、`spec`、`plan-tasks` などのスキルが一覧に出る
- `/hooks` でフックが認識されている(フックを入れた場合)

## Step 1: 最初の指示を出す

目的は、**いきなり作らせず、質問と提案だけをさせる**ことです。

1. `../prompts/00-first-instruction.md` を埋めます。
2. 作るものに合う種類別テンプレートを埋めて、続けて貼ります。

| 作るもの | 続けて貼るテンプレート |
|---|---|
| 静的ページ | `../prompts/01-static-page.md` |
| LP | `../prompts/02-landing-page.md` |
| HP | `../prompts/03-homepage.md` |
| Web アプリ | `../prompts/04-web-app.md` |
| レスポンシブ Web アプリ | `../prompts/05-responsive-web-app.md` |
| スマホアプリ(Flutter) | `../prompts/06-mobile-app-flutter.md` |
| ネイティブアプリ | `../prompts/07-native-app.md` |

**プランモード**(`Shift+Tab` で切替)にしておくと、承認前にファイルが変更されません。

### 貼り付ける指示(最小の例)

```text
【種類。例: Web アプリ】を作ります。
- 名前: 【ToDo メモアプリ】
- 目的: 【個人のやることを手軽に管理したい】
- 完成の定義: 【ブラウザで追加・完了・削除ができ、リロードしてもデータが残る】
- 技術: 【未定。2案を比較して提案してほしい】

進め方:
1. まず質問してください(不明点は最大5個)。
2. 次に、技術の提案(2案比較)と、作業の大まかな流れを出してください。
3. 私が承認するまで、ファイルの作成・変更はしないでください。
```

**Claude が返すもの**: 質問(最大5個)

## Step 2: 質問に答えて、方針を決める

質問に答えます。決められないものは「未定。おすすめを理由つきで」と返します。

### 返す指示の例

```text
回答します。
1. 【回答】
2. 【回答】
3. 未定。おすすめを理由つきで教えてください。
```

**Claude が返すもの**: 技術の提案(2案比較)、作業の大まかな流れ

### 方針を決める指示の例

```text
【案A】で進めます。理由は【〇〇】です。ここまでの内容で、決まったことと未決事項を整理してください。
```

**確認すること**

- 使う技術、実行環境、公開先が決まっている
- 「今回やらないこと」が見えている
- 分からないことを、Claude が推測で埋めていない(「未確認」と明記されている)

## Step 3: CLAUDE.md と Rules を作る

決まった内容を記録します。**短い案内・全体像は `CLAUDE.md`、中身(技術・コマンド・規約・作業ルール・注意事項)は `.claude/rules/`** に書きます。以降の Skills(`/test` など)は、`.claude/rules/commands.md` のコマンドを参照して動きます。

```text
/init
```

作られた `CLAUDE.md` の内容を、`../project-template/` の形に合わせて振り分けます。

```text
/init で作った CLAUDE.md の内容を、次のように振り分けてください。
- CLAUDE.md には、概要、ワークフローの Skills 一覧、ドキュメントの置き場所(docs/spec.md、docs/plan.md、docs/workflow.md)、Rules への案内だけを残す
- .claude/rules/tech-stack.md: 技術スタック(使わないものも)
- .claude/rules/commands.md: よく使うコマンド(テスト・lint・ビルド・開発サーバー)
- .claude/rules/code-style.md: コード規約
- .claude/rules/work-rules.md: 作業ルール(push は人が行う、既存ファイルの削除や依存追加は確認する、秘密情報はコミットしない)
- .claude/rules/cautions.md: 注意事項・落とし穴
../project-template/.claude/rules/ の形式に合わせてください。
```

| 書く内容 | 書く場所 | 読み込み |
|---|---|---|
| 概要、Skills 一覧、ドキュメントの場所 | `CLAUDE.md` | 毎回 |
| 技術スタック | `.claude/rules/tech-stack.md` | 毎回 |
| よく使うコマンド | `.claude/rules/commands.md` | 毎回 |
| 作業ルール | `.claude/rules/work-rules.md` | 毎回 |
| 注意事項・落とし穴 | `.claude/rules/cautions.md` | 毎回 |
| コード規約 | `.claude/rules/code-style.md` | 毎回(`paths` を付ければ、コードを触るときだけ) |

**確認すること**

- テスト・lint のコマンドが、実際に動くものになっている(未導入なら Step 6 の最初のタスクで整える)
- 秘密情報が書かれていない
- `/context all` の **Memory files** に、`CLAUDE.md` と `.claude/rules/` のファイルが出ている

## Step 4: 要件を整理する(`/spec`)

### 何が起きるか(Claude が質問して、人が答えて、文書になる)

`/spec` は、「やりたいこと」を、**あとから検証できる文書(`docs/spec.md`)にする**工程です。Claude が一方的に決めるのではなく、**質問 → 回答 → 文書化**の順に進みます。

```text
あなた: /spec 【概要】
   ↓ Claude が自動で行う
 1. CLAUDE.md、docs/、関連コードを読む。この会話で決まったこと(Step 1〜2)も前提にする
 2. 決まっていないことを洗い出す(目的、ユーザー、範囲、データ、非機能、連携)
 3. 結果が変わる重要なものだけ、最大5個、まとめて質問する(選択肢やおすすめ案つき)
   ↓ あなたが行う
 4. 質問に答える(決められないものは「おすすめで」)
   ↓ Claude が自動で行う
 5. docs/spec.md を書く(目的 / ユーザー / 機能要件 / 非機能要件 / 完了条件 / 未決事項)
 6. 回答がなく推測で埋めた項目に「【仮定】」を付け、報告する
   ↓ あなたが行う
 7. 内容を確認し、修正を依頼 → 次の Step 5 へ
```

| 項目 | どうなるか |
|---|---|
| 質問の作成 | **自動**(Claude が、不足している情報から作る) |
| 質問への回答 | **人が行う**(目的・範囲・優先度など、決めるのは人) |
| 文書の下書き | **自動**(回答と、既存資料・コードから作る) |
| 推測で埋めた部分 | **「【仮定】」と明記**される。人が確認して、確定または修正する |
| 仕様の確定 | **人が行う**(Claude は、依頼されていない要件を足さない) |
| 保存先 | `docs/spec.md` |

### 「要件が整理される」とは

曖昧な依頼を、次の形に変えることです。

| 整理前(依頼) | 整理後(`spec.md`) |
|---|---|
| ToDo アプリを作りたい | 目的: 個人のやることを手軽に管理する。ユーザー: 自分1人 |
| 追加・完了・削除ができる | 必須: 追加(タイトル必須、100文字まで)、一覧(未完了を上)、完了の切替、削除(確認つき) |
| 簡単に使えるように | 完了条件: キーボードだけで追加・完了・削除ができる |
| いろいろ便利に | 今回やらないこと: ログイン、通知、スマホアプリ化 |
| 動くようにしてほしい | 完了条件: `npm test` が通り、リロード後もデータが残る |

### 質問される内容の例

Claude は、次のような観点で、決まっていないことを質問します。

| 観点 | 質問の例 |
|---|---|
| 目的・成功の基準 | 何ができたら完成か。期限や規模の目安は |
| ユーザー・利用シーン | 誰が、どの端末で、どんな場面で使うか |
| 範囲 | 今回は入れない機能はどれか。優先度は |
| データ・入出力 | 何を保存するか。最大件数・文字数は。個人情報はあるか |
| 非機能 | セキュリティ、表示速度、対応ブラウザ、アクセシビリティの基準は |
| 連携・影響 | 外部サービスや、既存機能への影響はあるか |

### 良い回答の仕方

- **選択肢つきの質問には、番号で答える**(「1はA、2はB」)。
- **決められないものは、「おすすめで」と返す**。Claude が案を理由つきで出す。
- **「今回やらないこと」も答える**(範囲が膨らむのを防ぐ)。
- **回答の例**:

```text
回答します。
1. A(ログインなし)
2. 100文字まで
3. 期限日は今回やらない
4. おすすめで進めてください
5. Chrome の最新版だけでよい
```

### `/spec` の送り方(記載例)

`/spec` の後ろに書いた文章が、そのまま Claude への入力になります(Skill の `$ARGUMENTS`)。**メッセージの先頭に `/spec` を書いて**、続けて「何を作るか」を書きます。

#### 書く内容の目安

| 項目 | 書き方 | 例 |
|---|---|---|
| 何を作るか(必須) | 一言で | ToDo の追加・完了・削除ができる個人用メモアプリ |
| 誰が使うか | 人と端末・場面 | 自分1人、PC のブラウザ |
| 目的・ゴール | 何ができたら完成か | ブラウザで操作でき、リロード後もデータが残る |
| 決まっていること | 技術、環境、公開先 | Node.js + TypeScript、SQLite |
| やらないこと | 範囲を絞る | ログイン、通知は今回なし |
| 参考 | 資料・例 | `docs/idea.md`、参考にしたいアプリ |

全部は不要です。**「何を作るか」だけでも送れます**(足りない分は Claude が質問します)。

#### 例1: 最小(一言だけ)

```text
/spec ToDo の追加・完了・削除ができる個人用メモアプリ
```

→ 質問が多めになりますが、まず始めたいときはこれで十分です。

#### 例2: 標準(おすすめ)

```text
/spec ToDo メモアプリ。
- 使う人: 自分1人。PC のブラウザで使う
- やること: ToDo の追加・完了の切り替え・削除
- 完成の基準: リロードしてもデータが残る
- 決まっていること: Node.js + TypeScript、データは SQLite
- 今回やらないこと: ログイン、通知、スマホアプリ化
```

→ 質問が減り、`spec.md` の精度が上がります。

#### 例3: ファイルに書いて渡す(長い依頼・メモがあるとき)

`docs/idea.md` に、自由にメモを書いておきます(箇条書きでも、文章でもよい)。

```text
/spec docs/idea.md
```

→ `/spec` は、引数がファイルのパスなら、その内容を入力として読みます。
→ 書き方のひな形: `../prompts/11-spec-input.md`(何を作るか / 使う人 / 完成の基準 / やりたいこと / 決まっていること / やらないこと / 不安 / 参考資料)

#### 例4: 前の会話を引き継ぐ

Step 1〜2 で決めた内容が、同じ会話に残っている場合:

```text
/spec 上で決めた内容(Web アプリ、案A、SQLite)を前提に、ToDo の追加・完了・削除を整理してください
```

会話が新しくなっている場合は、決めた内容を書くか、`CLAUDE.md` に残してから送ります。

#### 例5: 既存のアプリに機能を追加する

```text
/spec 既存の ToDo アプリに「期限日」を追加したい。
- 期限日は任意入力。過ぎた ToDo は、一覧で赤く表示する
- 既存データは、期限日なしのまま残す
- 影響範囲は、コードを読んで調べてほしい
```

→ 既存コードを読んだうえで、影響範囲を含めて整理されます。

#### 例6: 参考を添える

```text
/spec 会員向けの予約ページ。参考: 【参考にしたいサービスの名前や、画面の特徴】。
ただし、決済と会員登録は今回やらない。
```

#### 種類別の例

作るものに合わせて、「何を」「誰が」「完成の基準」を変えます。

| 種類 | 送り方の例 |
|---|---|
| 静的ページ | `/spec 自己紹介の1ページ。スマホでも見られる。ビルドなし(HTML/CSS のみ)` |
| LP | `/spec 無料相談の申込を増やす LP。ターゲット: 30代の会社員。申込はフォーム。スマホ中心` |
| HP | `/spec 美容室のホームページ。ページ: トップ、メニュー、料金、アクセス、予約(外部サービスへのリンク)。更新は自分でお知らせだけ` |
| Web アプリ | `/spec 社内の備品貸出管理。ログインあり。管理者と一般の2権限。貸出・返却・履歴。PC のみ` |
| レスポンシブ Web アプリ | `/spec 現場スタッフがスマホで日報を入力し、管理者が PC で集計するアプリ。スマホ中心、通信が不安定なこともある` |
| スマホアプリ(Flutter) | `/spec 習慣トラッカーの iOS/Android アプリ。データは端末内。通知は今回なし` |
| ネイティブアプリ | `/spec iPhone 向けの歩数記録アプリ。ヘルスケアのデータを読む。iOS のみ` |

#### 避けたい送り方

| 悪い例 | 問題 | 良い例 |
|---|---|---|
| `/spec いい感じのアプリ` | 何を作るか分からず、質問が増える | `/spec 家計簿アプリ。収入と支出を記録し、月ごとに集計する` |
| `/spec ToDo アプリ。全部入りで` | 範囲が膨らむ | `/spec ToDo アプリ。追加・完了・削除だけ。他は今回やらない` |
| `/spec 使いやすくして` | 検証できない | `/spec キーボードだけで追加・完了・削除ができるようにしたい` |
| `spec ToDo アプリ`(`/` なし) | Skill として実行されない | `/spec ToDo アプリ` |
| 文中に `/spec` を書く(「次に /spec で…」) | 直接実行にならない | メッセージの**先頭**に `/spec` |

#### 改行して長く書きたいとき

端末で改行を入れにくい場合は、ファイルに書いて渡すのが確実です(例3)。

```text
/spec docs/idea.md
```

#### 送ったあとの流れ

1. Claude が、質問(最大5個)を返す
2. 番号で答える(「1はA、2はB、3はおすすめで」)
3. `docs/spec.md` が作られる。「【仮定】」の項目を確認する

### 確認すること

- 必須 / あると良い / 今回やらないこと が分かれている
- **完了条件が、検証できる形(チェックリスト)になっている**
  - ○「スマホ幅 375px で横スクロールが出ない」「100文字を超えると、エラーが出て追加されない」
  - ×「見やすい」「使いやすい」「ちゃんと動く」
- **「【仮定】」の項目を、1つずつ確認する**(正しければ外し、違えば直す)
- 未決事項が、この先で決める時期とともに残っている
- 依頼していない機能が、勝手に入っていない

### 修正を依頼する指示の例

```text
完了条件に「削除前に確認ダイアログが出る」を追加してください。
```

```text
「あると良い」の検索機能は、今回やらないことに移してください。
```

```text
【仮定】の項目のうち、2つ目は正しいです。3つ目は【〇〇】に直してください。
```

```text
未決事項をすべて、「おすすめ」で決めてください。決めた理由も書いてください。
```

### 補足

- **会話が新しくなっている場合**(`/clear` の後や、別の日に始めた場合)、Step 1〜2 の合意は、Claude から見えません。`CLAUDE.md` に書くか、`/spec` の入力として渡してください。
- **小さな修正**や、仕様がすでに固まっている場合は、`/spec` を省いて構いません(完了条件だけは1行でも決めてください)。
- **仕様が途中で変わったら**、先に `docs/spec.md` を更新してから、`/plan-tasks` で計画に反映します。

## Step 5: 計画を立てる(`/plan-tasks`)

### 何が起きるか(自動なのは「下書きの作成」まで)

`/plan-tasks` は、あなたが呼んだときに、Claude が次の順で**計画の下書きを作ります**。

```text
あなた: /plan-tasks 【機能名】
   ↓ Claude が自動で行う
 1. docs/spec.md を読む(なければ /spec を先に提案して止まる)
 2. 関連する既存コードを読み、影響する範囲を洗い出す
 3. 作業を、1タスク=1つの検証可能な変更に分解する
 4. 各タスクに「変更予定のファイル」「確認方法」「依存するタスク」を書く
 5. リスクと代替案を書く
 6. docs/plan.md に保存し、要約して「承認を待つ」
   ↓ あなたが行う
 7. 内容を確認し、修正を依頼 → 承認
```

| 項目 | どうなるか |
|---|---|
| タスクの作成 | **自動**(Claude が `spec.md` とコードから下書きを作る) |
| タスクの内容の正しさ | **人が確認**(Claude は推測で分解するので、抜けや粒度のずれがありうる) |
| 承認 | **人が行う**(承認前は実装しない) |
| 保存先 | `docs/plan.md`(ファイル。Issue ではない) |
| GitHub Issue の作成 | **自動では作られない**(下の「Issue にしたい場合」を参照) |

### `/plan-tasks` の送り方(記載例)

`/plan-tasks` の後ろに書いた文章が、そのまま Claude への入力になります(Skill の `$ARGUMENTS`)。**メッセージの先頭に `/plan-tasks` を書いて**、続けて「どの機能(範囲)の計画か」を書きます。計画の材料は `docs/spec.md` なので、**先に `/spec` を終えておいてください**(なければ、Claude が `/spec` を提案して止まります)。

#### 書く内容の目安

| 項目 | 書き方 | 例 |
|---|---|---|
| 対象の機能・範囲(必須) | 機能名、または「全体」 | ToDo の追加・完了・削除 |
| 粒度の希望 | 1タスクの大きさ | 1回の実装で終わり、確認方法が1つに決まる大きさ |
| 技術・方針の指定 | 決まっていることと、比較してほしいこと | DB は SQLite。画面は、2案を比較して提案 |
| 優先する順序 | 先にやりたいもの | まず動く最小の流れ(追加と一覧)から |
| 制約 | 守ってほしいこと | 依存パッケージは増やさない |
| 調査の依頼 | 既存コードの確認 | 影響を受ける箇所を、先に調べてほしい |

**「対象の機能」だけでも送れます。** 粒度や順序は、Skill の標準の基準(1回の `/implement` で終わる大きさ、土台 → データ → API → 画面 → 仕上げ)で作られます。

#### 例1: 最小(機能名だけ)

```text
/plan-tasks ToDo の追加・完了・削除
```

→ `docs/spec.md` の内容から、タスクの下書きが `docs/plan.md` に作られます。

#### 例2: 標準(おすすめ)

```text
/plan-tasks ToDo の追加・完了・削除。
- 1タスクは、1回の /implement で終わり、確認方法が1つに決まる大きさにする
- まず「追加と一覧が動く」最小の流れを作り、完了の切り替えと削除は後にする
- 技術の選択が複数ある場合は、2案を比較して提示する
- 今回やらないことと、その理由も書く
```

→ 順序と粒度の希望が反映され、比較案も出ます。

#### 例3: 先に調査させてから計画する(既存コードがある場合)

```text
researcher で、src/db と src/api の構造と、「期限日」の追加で影響を受けそうな箇所を調べて。
その結果を踏まえて /plan-tasks 期限日の追加 を実行してください。
```

→ 調査(別コンテキスト)の要約をもとに、計画が作られます。

#### 例4: 制約をつける

```text
/plan-tasks 全体。
- 依存パッケージは増やさない
- DB のスキーマ変更が必要なタスクは、必ず単独のタスクにする
- 各タスクに、確認するコマンドを書く
```

#### 例5: 一部だけ計画する(大きな仕様の一部)

```text
/plan-tasks 仕様のうち「ユーザー登録とログイン」だけ。他の機能は、まだ計画しない
```

#### 例6: 既存の計画を更新する(仕様が変わった・追加した)

```text
/plan-tasks 全体。docs/spec.md に「検索機能」を追加したので、docs/plan.md に反映してください。
完了済みのタスクは変更せず、新しいタスクを末尾に追加してください。
```

→ 完了済みのタスクを保ったまま、差分だけ追加させる頼み方です。

#### 種類別の例

作るものに合わせて、「対象」と「先に動かしたいもの」を変えます。

| 種類 | 送り方の例 |
|---|---|
| 静的ページ | `/plan-tasks 全体。まず共通のヘッダー・フッターと見た目の土台、次にセクションごと、最後にスマホ対応の確認` |
| LP | `/plan-tasks 全体。ファーストビュー → 特長 → 実績 → フォーム → 計測の順。フォームの送信先は、2案を比較して提案` |
| HP | `/plan-tasks 全体。共通部分 → トップ → 下層ページ → お問い合わせフォームの順。ページごとに1タスク` |
| Web アプリ | `/plan-tasks 全体。DB → API → 画面の縦に薄い単位で、1機能ずつ。認証は最初のタスクの1つにする` |
| レスポンシブ Web アプリ | `/plan-tasks 全体。共通レイアウトをスマホ幅で作り、各画面をスマホ → PC の順に広げる。幅ごとの確認方法を書く` |
| スマホアプリ(Flutter) | `/plan-tasks 全体。環境確認(flutter doctor)→ 画面1つずつ(UI → 状態管理 → データ → テスト)` |
| ネイティブアプリ | `/plan-tasks iOS 版。環境確認 → 画面1つずつ。権限とバックグラウンド処理は単独のタスクにする` |

#### 避けたい送り方

| 悪い例 | 問題 | 良い例 |
|---|---|---|
| `/plan-tasks`(何も書かない) | 範囲が不明で、全体を広く計画しすぎることがある | `/plan-tasks ToDo の追加・完了・削除` |
| `/plan-tasks 全部いい感じに` | 粒度・順序が決まらない | `/plan-tasks 全体。1タスクは1回の実装で終わる大きさに` |
| `/plan-tasks 実装して` | 計画ではなく実装を求めている | 計画の承認後に `/implement 1` |
| `/spec` を終えずに送る | 材料(`docs/spec.md`)がない | 先に `/spec` を実行 |
| `plan-tasks ToDo`(`/` なし) | Skill として実行されない | `/plan-tasks ToDo` |
| 文中に `/plan-tasks` を書く | 直接実行にならない | メッセージの**先頭**に書く |

#### 送ったあとの流れ

1. Claude が `docs/plan.md` を作り、要約して**承認を待つ**
2. 粒度・順序・抜けを確認し、修正を依頼する(下の「修正を依頼する指示の例」)
3. 問題なければ「承認します」と返す
4. `/implement 1` で、最初のタスクを実行する

### タスクの粒度の基準

Claude に任せる場合も、確認するときも、次の基準で見ます。

- **1タスク=1つの目的**で、1回の `/implement` で終わる大きさ(目安: 変更ファイルが数個、確認方法が1つ)
- **確認方法がある**(テスト、コマンド、画面での確認)。確認できないタスクは、大きすぎるか曖昧
- **順序に理由がある**(土台 → データ → API → 画面 → 仕上げ)。依存関係が書かれている
- **仕様にないことが入っていない**(入っていれば、`spec.md` を先に更新するか、タスクから外す)

### 計画の質を上げる頼み方

```text
/plan-tasks 【機能名】
ただし次を守ってください。
- 1タスクは、1回の /implement で終わり、確認方法が1つに決まる大きさにする
- 技術の選択が複数ある場合は、2案を比較して提示する
- 計画に入れなかったこと(今回やらないこと)も、理由つきで書く
```

調査が必要な場合は、先に調べさせます。

```text
researcher で、【関連する部分】の構造と、影響を受けそうな箇所を調べて。その結果を踏まえて /plan-tasks 【機能名】 を実行してください。
```

### 確認すること

- 1タスク=1つの検証可能な変更になっている
- 順序と依存関係が妥当
- 各タスクに、確認方法がある
- 「今回やらないこと」が、`spec.md` と一致している
- 抜けているタスクがない(エラー処理、テスト、README など)

### 修正を依頼する指示の例

```text
タスク3と4をまとめてください。タスク6は、タスク2の前に移してください。
```

```text
タスク5が大きすぎます。確認方法が1つに決まるよう、2つに分けてください。
```

```text
エラー時の表示のタスクが抜けています。タスク4の後に追加してください。
```

問題なければ:

```text
承認します。
```

### Issue にしたい場合(任意。別の Skill)

`docs/plan.md` のタスクを、GitHub Issue にすることもできます。ただし、**標準の7つの Skills には含まれておらず、自動では作られません。** 追加のテンプレートを用意しています。

- `../project-template/optional/skills/plan-to-issues/SKILL.md`(`/plan-to-issues`)
- 使う条件: GitHub にリポジトリがあり、`gh` コマンド(GitHub CLI)がログイン済みであること
- 動き方: 計画のタスクから、作る Issue の一覧(タイトル・本文・ラベル)を**先に提示**し、あなたの確認後に作成。作った Issue の番号を `docs/plan.md` に書き戻す
- 自動で作らない理由: Issue は外部(GitHub)に残り、通知も飛ぶため、人が確認してから作る

```text
/plan-to-issues
```

**どちらを正とするか**を、最初に決めてください。

| 運用 | 向いている場面 |
|---|---|
| `docs/plan.md` だけ(Issue なし) | 個人・小規模。ファイルだけで完結し、Claude が一番扱いやすい |
| `plan.md` + Issue | チームで担当や議論を管理したい。`plan.md` にはタスク番号と Issue 番号を対応させる |

両方を更新し続けると、ずれやすくなります。Issue を使う場合も、`/implement` の指示は、`plan.md` のタスク番号で行うのが簡単です。

## Step 6: タスクを1つずつ進める

計画(`docs/plan.md`)のタスクのうち、**どれをやるかは、あなたが番号で指示します**(各コマンドの意味と、番号の見方は、冒頭の「コマンド早見表」を参照)。1タスクごとに、次のサイクルを回します。

```text
/implement N → /test → /review → (指摘があれば修正 → /test) → /commit → /implement N+1
作る(Nは計画の番号) 確かめる 点検する    (直す → 確かめる)         記録する    次のタスクを作る
```

以下では、**各指示を送ると、Claude がどう動き、何を返すか**を、ToDo アプリのタスク3(「ToDo の追加 API と入力検証」)を例に説明します。出力の例は、動きのイメージを示すためのもので、実際の文面や内容は、プロジェクトや Claude の判断で変わります。

| 工程 | 送る指示 | Claude の動き(要約) | 返ってくるもの |
|---|---|---|---|
| 実装 | `/implement 3` | 計画のタスク3だけを実装し、テストも追加・実行する | 変更ファイル、テスト結果、確認方法、気づいた点 |
| テスト | `/test` | テストと lint を実行し、失敗があれば原因を調べて直す | 実行コマンド、結果の件数、直した内容 |
| レビュー | `/review` | 別コンテキストで、差分を読み取り専用でレビューする | 重要度順の指摘(ファイル・行・問題・改善案) |
| コミット | `/commit` | 差分と混入物を確認し、1つの目的でコミットする | コミットのハッシュとメッセージ |

---

### 6-1. 実装する(`/implement`)

#### 送り方

メッセージの**先頭**に `/implement` を書き、続けて**タスクの番号**(またはタイトル)を書きます。

```text
/implement 3
```

補足を添えることもできます。

```text
/implement 3。入力検証のエラーメッセージは日本語にしてください
```

```text
/implement タスク3(ToDo の追加 API と入力検証)
```

#### どう動くか

1. `CLAUDE.md`、`docs/spec.md`、`docs/plan.md` の該当部分を読む。タスクが特定できなければ質問する
2. 変更するファイルの周辺コードを読み、既存の規約・命名に合わせる
3. **タスク3の範囲だけ**を実装する(範囲外の改善はしない。気づいた点は報告に書く)
4. 対応するテストを追加・更新する
5. `.claude/rules/commands.md` のテスト・lint のコマンドを実行し、失敗したら直す
6. `docs/plan.md` のタスク3を、完了の印とメモつきで更新する
7. 報告する

途中で、削除、依存パッケージの追加、設定の大きな変更が必要になったら、**実行前にあなたへ確認します**。コミットはしません。

#### 返ってくる報告の例

```text
タスク3「ToDo の追加 API と入力検証」を実装しました。

変更したファイル
- src/api/todos.ts(新規): POST /todos。タイトルが空、または101文字以上は 400 を返す
- tests/api.test.ts(新規): 正常値・空文字・100文字・101文字のテスト4件
- docs/plan.md: タスク3を完了に更新

テスト結果
- npm test: 4件追加、全件成功(合計 9件)
- npm run lint: 警告なし

確認方法
- npm run dev を起動し、curl -X POST localhost:3000/todos -d '{"title":"牛乳を買う"}' で 201 が返る

気づいた点(今回は対応していません)
- GET /todos のレスポンス形式が未定義です。タスク4で決めるのがよさそうです
```

#### 確認すること

- 変更ファイルが、計画の「変更予定のファイル」と大きくずれていない
- 「気づいた点」が、計画の次のタスクや、`spec.md` の更新が必要な内容でないか
- 報告の確認方法を、自分でも1回試す

#### うまくいかないときの指示

| 状況 | 送る指示 |
|---|---|
| 範囲外の変更が入っている | `タスク3の範囲外の変更(〇〇)を戻してください。気づいた点として報告だけにしてください` |
| 内容が計画と違う | `計画のタスク3の確認方法は【〇〇】です。それを満たすよう直してください` |
| 大きすぎて終わらない | `タスク3を2つに分けてください。docs/plan.md を更新してから、最初の方を実装してください` |
| 仕様の抜けに気づいた | `docs/spec.md に【〇〇】を追加してから、タスク3を続けてください` |

---

### 6-2. テストする(`/test`)

#### 送り方

```text
/test
```

対象を絞る場合は、ファイルやテスト名を添えます。

```text
/test tests/api.test.ts
```

失敗を調べさせたい場合は、状況を添えます。

```text
/test 追加の API のテストが1件落ちています。原因を調べて直してください
```

#### どう動くか

1. `.claude/rules/commands.md` のテスト・lint のコマンドを確認する
2. 対象のテストと lint を実行する(`allowed-tools` に許可したコマンドは、確認なしで実行される)
3. 失敗があれば、失敗したテスト名とエラーを整理し、**テストの誤りか、実装の誤りか**を切り分けて調べる
4. 実装を直し、再実行して通ることを確認する(**テストを弱めて通すことはしない**)
5. 報告する

仕様の変更が必要そうな場合は、修正せずに報告します。

#### 返ってくる報告の例(成功)

```text
実行したコマンド: npm test、npm run lint
結果: テスト 9件すべて成功、lint 警告なし
残っている問題: なし
```

#### 返ってくる報告の例(失敗 → 修正)

```text
実行したコマンド: npm test、npm run lint
結果: 1件失敗(合計 9件中 8件成功)

失敗したテスト
- 「101文字のタイトルは拒否される」: 期待 400、実際 201

原因: 文字数の検証が `>= 101` ではなく `> 101` になっており、境界値(101文字)が通っていました。実装の誤りです。
修正: src/api/todos.ts の検証を `> 100` に変更しました。

再実行: 9件すべて成功
```

#### 確認すること

- 「テストを削除・スキップして通した」という説明になっていない
- 原因の説明が、実装の誤りかテストの誤りか、明確になっている
- 仕様の問題と報告された場合は、**`/test` ではなく、`docs/spec.md` を先に直す**

---

### 6-3. レビューする(`/review`)

#### 送り方

```text
/review
```

観点を絞る・追加する場合は、依頼文で伝えます。

```text
/review セキュリティと入力検証を重点的に見てください
```

#### どう動くか

1. **別のコンテキスト(読み取り専用のサブエージェント)**で実行される。この会話の履歴は見えない
2. 実行時に `git status` と `git diff HEAD`(**まだコミットしていない変更**)が埋め込まれる
3. 差分と周辺のコードを読み、観点(バグ、セキュリティ、仕様との一致、可読性、テスト不足)で指摘をまとめる
4. **ファイルは変更しない**(報告のみ)

> **注意:** 差分は「コミット前の変更」です。**`/commit` の前に `/review` を実行してください。** コミット後に実行すると、差分が空になります。コミット済みの変更を見たい場合は、`/review 直前のコミット(git show HEAD)をレビューして` のように頼みます。

#### 返ってくる報告の例

```text
重要度: 高
- src/api/todos.ts:18 — タイトルをそのまま SQL 文字列に連結しています。SQL インジェクションの可能性があります。
  改善案: プレースホルダー(パラメータ化クエリ)を使う。

重要度: 中
- src/api/todos.ts:25 — DB エラー時に、内部のエラーメッセージをそのままレスポンスに含めています。
  改善案: 利用者向けの固定メッセージを返し、詳細はログに出す。

重要度: 低
- tests/api.test.ts:40 — テスト名が「test2」で、何を確認するか分かりません。
  改善案: 「101文字のタイトルは拒否される」のように、振る舞いが分かる名前にする。
```

問題がなければ、「重大な問題は見つかりませんでした」と、確認した観点が1行で返ります。

#### 指摘への対応を指示する

| 状況 | 送る指示 |
|---|---|
| 重要なものだけ直す | `レビューの指摘のうち、重要度「高」と「中」を修正してください。修正後に /test を実行してください。` |
| すべて直す | `レビューの指摘をすべて修正してください。修正後に /test を実行してください。` |
| 一部は直さない | `1つ目と3つ目を修正してください。2つ目は、今回は対応しません(理由: 内部ツールのため)` |
| 指摘が正しいか分からない | `2つ目の指摘は、実際に起きるのか、コードを読んで確認してください。直すかどうかは、その後に判断します` |
| 修正した後 | `/test` → 必要なら、もう一度 `/review` |

#### 確認すること

- 指摘を**鵜呑みにしない**。レビューは、読み取りと推測による指摘で、誤りや過剰な指摘もありうる(特にセキュリティの「高」は、自分でも確認する)
- 直さない指摘は、理由をメモしておく(後で `docs/plan.md` や Issue に残してもよい)

---

### 6-4. コミットする(`/commit`)

#### 送り方

```text
/commit
```

メッセージの方針を伝える場合:

```text
/commit メッセージは日本語で。タスク3と分かるように書いてください
```

#### どう動くか

1. 実行時に `git status` と、直近のコミット5件が埋め込まれる
2. 差分を確認し、変更が**1つの目的**にまとまっているか確認する(混ざっていれば、分けることを提案する)
3. 秘密情報(`.env`、キー)や不要なファイル(ビルド成果物、一時ファイル)が含まれていないか確認する。あれば、ステージせずに報告する
4. 関連するファイルだけを個別に `git add` する(`git add -A` は避ける)
5. 直近のコミットの書式に合わせて、メッセージを書いてコミットする
6. 報告する

**`git push` は行いません**(許可していない。Hook と権限設定でも止まる)。コミットのフック(pre-commit など)が失敗した場合は、`--no-verify` で回避せず、原因を報告して直します。

#### 返ってくる報告の例

```text
コミットしました。
- a1b2c3d: ToDo の追加 API と入力検証を追加(タスク3)

含めたファイル: src/api/todos.ts、tests/api.test.ts、docs/plan.md
含めなかったファイル: なし
push はしていません。必要なら、あなたが実行してください。
```

#### 確認すること

- メッセージが、「何を」「なぜ」を表している
- 含めたファイルが、タスクの範囲と一致している
- `git log --oneline -3` で、コミットが入っていることを確認する

#### うまくいかないとき

| 状況 | 送る指示 |
|---|---|
| 複数の目的が混ざっていた | `機能追加と、リファクタリングを、別々のコミットに分けてください` |
| メッセージを直したい | `直前のコミットメッセージを、【〇〇】に直してください(まだ push していません)` |
| pre-commit が失敗した | `失敗の原因を調べて直してください。--no-verify は使わないでください` |
| ファイルを含め忘れた | `docs/plan.md を、直前のコミットに追加してください(まだ push していません)` |

---

### 6-5. 次のタスクへ進む・途中で状況が変わったとき

#### 次のタスクへ

```text
/implement 4
```

「次のタスクを進めて」と頼むこともできますが、その場合は Claude が `docs/plan.md` を読んで判断します。**番号で指定するほうが確実です。**

#### 状況別の指示

| 状況 | 送る指示 |
|---|---|
| 現在地が分からない・会話が切れた | `docs/plan.md と git log を見て、現在地と次のタスクを教えてください。` |
| タスクの順序を変えたい | `タスク6を、タスク4の前に移してください(docs/plan.md を更新)。` |
| タスクを飛ばしたい | `タスク5は、今回はやらないことにします。docs/plan.md で「見送り」にして、理由を書いてください。` |
| タスクをやり直したい | `タスク3の実装を、計画の確認方法を満たすようにやり直してください。変更は戻して構いません。` |
| 計画にないバグを見つけた | `タスク4の途中で、【〇〇】のバグに気づきました。docs/plan.md に新しいタスクとして追加してください。今のタスクは、続けます。` |
| 仕様が変わった | `docs/spec.md を更新します。変更点を反映して /plan-tasks で、docs/plan.md を更新してください。完了済みは変更しないでください。` |
| 複数のタスクをまとめて頼みたい | 1タスクずつを勧めます(範囲が広がると、確認とレビューが難しくなる)。どうしても頼むなら、`タスク4と5を、順に実装してください。それぞれの後に /test を実行して報告してください` |

---

### 6-6. 1タスクの通しの例(会話のイメージ)

```text
あなた:  /implement 3
Claude:  (実装して、報告)変更ファイル、テスト4件追加・全件成功、確認方法、気づいた点

あなた:  /test
Claude:  9件すべて成功、lint 警告なし

あなた:  /review
Claude:  重要度「高」1件(SQL の文字列連結)、「中」1件、「低」1件

あなた:  レビューの指摘のうち、重要度「高」と「中」を修正してください。修正後に /test を実行してください。
Claude:  (修正して、テスト実行)9件すべて成功

あなた:  /commit
Claude:  a1b2c3d: ToDo の追加 API と入力検証を追加(タスク3)。push はしていません

あなた:  /implement 4
Claude:  (タスク4へ)
```

### 途中で確認すること

- 各タスクの終わりで、`docs/plan.md` の該当タスクが `[x]` になっている
- 計画にない変更が入っていない(入っていたら、理由を聞く。必要なら `docs/spec.md` を先に更新)
- `git push` やデプロイを Claude がしていない(Hooks と権限設定で止まる)
- 各工程で、**報告を読んでから次へ進む**(報告を読まずに連続で送らない)

### 途中で会話が切れたとき

```text
docs/plan.md と git log を見て、現在地と次のタスクを教えてください。
```

`SessionStart` のフック(`show-progress.sh`)を入れていれば、再開時に未完了タスクも表示されます。

### 注意

- 上の報告の文面は、動きのイメージを示す例です。実際の出力は異なります。
- 「直前のコミットを直す」などの指示は、Git の履歴を書き換える操作を含みます。`push` 前に限り、内容を確認してから使ってください(`/commit` Skill は履歴の書き換えを許可していないため、通常の依頼として頼む形になります。その場合の許可は、権限設定に依存します)。

## Step 7: 公開前のチェック(`/release`)

すべてのタスクが完了したら:

```text
/release 【バージョン。例: 0.1.0】
```

**Claude が返すもの**

- チェック結果(OK / 要対応)
- 要対応の項目と対処の提案
- リリースノートの下書き
- 公開のために**あなたが実行する手順**

**確認すること**

- `docs/spec.md` の完了条件が、すべて満たされている
- テスト・lint・ビルドが通る
- 秘密情報がコミットされていない

---

## Step 8: 公開(人が行う)

`git push`、デプロイ、タグ付け、ストア申請は、**あなたが行います**。Claude は実行しません。

```bash
git push origin main
```

## 流れを短くしたいとき

| 場面 | 省略できるもの |
|---|---|
| 小さな修正 | `/spec` と `/plan-tasks` を省き、修正内容を通常の依頼で伝える(実装後に `/test`) |
| 規模が小さい新規作成 | `/spec` を省き、Step 1〜2 の合意を `/plan-tasks` の入力にする |
| 計画が固まっている | Step 1〜2 を省き、`/spec` から始める |
| 公開しない試作 | `/release` を省く |

省いた場合も、次は守ってください。

- 実装前に、完了条件を決める(1行でもよい)
- コミット前に、テストを通す
- `push` と公開は人が行う

## 各ステップで困ったとき

| 症状 | 対処 |
|---|---|
| Claude がいきなり実装を始めた | 止めて、「承認前にファイルを変更しないでください。プランモード(`Shift+Tab`)に切り替えます」と伝える |
| 質問が多すぎる・少なすぎる | 「質問は最大5個にまとめて」「決められないものは、おすすめで進めて」と伝える |
| `/spec` の内容が Step 2 の合意とずれる | 「Step 2 で決めた【〇〇】を反映してください」と指摘する |
| 計画が大きすぎる | 「タスクを、1つ1時間以内で確認できる粒度に分けてください」と伝える |
| 同じ指摘を何度もする | `CLAUDE.md` か Rules に書く(`read/03-rules.md`)。強制したいなら Hooks / 権限へ |
| スキルが一覧に出ない | `.claude/skills/<name>/SKILL.md` の場所を確認し、`/reload-skills` か再起動 |

## 配置場所(使うときに、どこに置くか)

この手引きを進めると、自分のプロジェクトに次のファイルが**置かれる・作られる**場所は、こうなります。

| ファイル | 誰が置く・作るか | 場所(自分のプロジェクト) | ステップ |
|---|---|---|---|
| `CLAUDE.md`、`.claude/` 一式、`docs/workflow.md` | 人(`../project-template/` からコピー) | プロジェクトのルート | Step 0 |
| 最初の指示(埋めたもの) | 人(任意で保存) | `docs/brief.md` など | Step 1〜2 |
| `.claude/rules/*.md`(技術・コマンド・規約 など) | Claude(`/init` の結果を振り分け)+ 人が確認 | `.claude/rules/` | Step 3 |
| アイデアメモ | 人 | `docs/idea.md` | Step 4 |
| `docs/spec.md` | Claude(`/spec`) | `docs/` | Step 4 |
| `docs/plan.md` | Claude(`/plan-tasks`)。`/implement` が進捗を更新 | `docs/` | Step 5〜6 |
| ソースコード、テスト | Claude(`/implement`) | プロジェクトの `src/`、`tests/` など | Step 6 |
| コミット | Claude(`/commit`)。push は人 | git | Step 6〜8 |

```text
<自分のプロジェクト>/
├── CLAUDE.md
├── docs/
│   ├── workflow.md          ← Step 0 でコピー
│   ├── brief.md / idea.md   ← (任意)Step 1・4 で人が置く
│   ├── spec.md              ← Step 4 で作られる
│   └── plan.md              ← Step 5 で作られ、Step 6 で更新される
├── .claude/                 ← Step 0 でコピー(rules は Step 3 で内容を埋める)
└── src/ tests/ ...          ← Step 6 で作られる
```

- この手引き自体(`13-...md`)と、指示の雛形(`../prompts/`)は、**雛形集に置いたまま**参照します。自分のプロジェクトにはコピーしなくて構いません。
- 手引きの中の `docs/`、`.claude/`、`CLAUDE.md` は、**自分のプロジェクト**のファイルを指します。`../prompts/`、`../project-template/` は、雛形集を指します。

- 貼り付ける指示文は例です。プロジェクトに合わせて書き換えてください。
